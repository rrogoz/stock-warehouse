## Goal

`python -m engine run` runs the pipeline steps in order and owns the run id, the run log and publish last, so every later M1 story only plugs a step in ([ADR-007](../adr/0007-pipeline-engine-and-operations.md), [ADR-003](../adr/0003-storage-and-physical-format.md)). M1 seed item 1 in the [overview](../overview.md); deliverable 7.

## Design

**Command.** `python -m engine run` runs a run and exits 0 on success, 1 on a failed step or publish, 2 on bad configuration. Its last stdout line is `run <run_id> <status>`, which the runbook tells Rafal to check. `python -m engine` without a subcommand keeps printing the version and exits 0, so the CI docker job stays green. The step list is `STEPS` in `pipeline.py`, empty in this story; later stories append to it. A step is a `Protocol`: `name: str` and `run(ctx) -> int`, returning its row count. `ctx` holds `run_id`, an open DuckDB connection on the working copy, and the storage.

**Configuration,** environment variables only, read once into a frozen dataclass; no environment names in code ([ADR-002](../adr/0002-runtime-and-environments.md)):

| Variable | Meaning |
| --- | --- |
| `SW_STORAGE_BACKEND` | `local` or `s3`; nothing else picks the backend |
| `SW_STORAGE_ROOT` | folder for `local` (DEV default `data/`, gitignored) |
| `SW_STORAGE_ENDPOINT`, `_BUCKET`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY` | R2 for `s3`, already in `.env.example` |
| `SW_IMAGE_TAG` | the image's tag, set by `ARG`/`ENV` in the `Dockerfile` at build time; default `local` |

A missing variable for the chosen backend is a clear error and exit 2.

**Storage** (`storage.py`): one `Storage` protocol on string keys: `read_bytes`, `write_bytes`, `download(key, path)`, `upload(path, key)`, `exists`, `list(prefix)`, `delete`. `LocalStorage(root)` writes to a temporary file then `os.replace`, so a reader never sees half an object. `S3Storage` uses `boto3` with the R2 endpoint; a single put is atomic. `from_config(cfg)` is the only place that chooses.

**Bucket layout,** documented in the `storage.py` module docstring (its home):

```text
warehouse/current.json                         pointer: {"version": 1, "database": "<key>"}
warehouse/sw_<YYYYMMDDTHHMMSSZ>_<run_id>.duckdb  one per published run; names sort by date
ops/run_log/<run_id>/started.json              written when the run starts
ops/run_log/<run_id>/ended.json                written when it ends: status, step counts
```

**Run, in order** (`pipeline.py`):

1. New `run_id` (`uuid4`, hex). Write `started.json` (`run_id`, `started_at`, `image_tag`); its write time is `started_at`.
2. Read the pointer; download the file it names into a temporary folder. That copy is the working copy; the original is never touched. No pointer yet: start from an empty file.
3. Read the rows the copy already holds in `silver.ops_run_log`, then rebuild the table from all run log objects (rules below).
4. Run each step in order; record its row count.
5. Insert this run's row into the copy with `status` `succeeded`, `ended_at` the time of this step and `failed_step` null. Close the copy, upload it as a new dated key, then overwrite the pointer. The pointer is the last write, so an interruption before it leaves the old version current ([ADR-003](../adr/0003-storage-and-physical-format.md)).
6. Retention: delete `warehouse/sw_*.duckdb` beyond the newest 14, never the one the pointer names. A delete error is logged, not fatal; the next run retries.
7. Write `ended.json` (`ended_at`, `status`, `step_row_counts`, `failed_step`). For a published run, `ended_at` is the same value step 5 put in the row, so the row never changes later. If this write fails after publish, it is logged; the run stays published and exits 0. The next run's step 3 keeps the row from step 5.

A step that raises `Exception` stops the run: no upload, no pointer change, `ended.json` with `failed`, the step name and the error logged, exit 1. A failed upload or pointer write is handled the same way (`failed_step` `publish`).

**Run log** (`run_log.py`). The objects under `ops/run_log/` are the permanent record: insert-only, written outside the database file, so a failed run that never publishes is still recorded (story criterion 4) and the table can always be rebuilt, like the database itself. `silver.ops_run_log` holds one row per run:

| Column | Type | Meaning |
| --- | --- | --- |
| `run_id` | varchar | business key |
| `business_date` | date | UTC date of `started_at`; a run has no market date ([ADR-003](../adr/0003-storage-and-physical-format.md)) |
| `known_at` | timestamptz, UTC | `ended_at` for an ended run (for a published run, the step-5 time that `ended.json` repeats), or `started_at` for an `interrupted` run (only `started.json` exists), so it is never null and never changes |
| `started_at`, `ended_at` | timestamptz, UTC | `ended_at` null if interrupted |
| `status` | varchar | `succeeded`, `failed`, or `interrupted` (started, never ended) |
| `image_tag` | varchar | code version, for replay ([ADR-007](../adr/0007-pipeline-engine-and-operations.md)) |
| `step_row_counts` | json | rows per step name, for example `{"fetch_nbp": 31}` |
| `failed_step` | varchar | null unless `failed` |

**Rebuild rule** (step 3). One row per run, from its objects. The rebuild is a full rebuild from the permanent record, like a rebuild from bronze, and gives the same row for a run every time, so a row is never updated in place (insert-only, [ADR-004](../adr/0004-physical-data-model.md)). `ended.json` wins when it exists. Without it, the run keeps the row its published copy already holds (step 5 of that run). Only a run with neither is `interrupted`. So a published run whose `ended.json` write failed still shows `succeeded`. Accepted: a failed run whose `ended.json` could not be written shows `interrupted`; nothing was published, so no data is wrong.

**Standard columns.** ADR-003 requires a business date, a knowledge time and a run id on silver records, and `ops_run_log` carries all three (`business_date`, `known_at`, `run_id`). [ADR-004](../adr/0004-physical-data-model.md) says "`known_at` comes from bronze: when the raw file was fetched, never the run time". An `ops_` entity has no bronze, so its `known_at` is the engine's write time: a deliberate deviation for `ops_` entities, named here for gate 2. ADR-004 also lists `source` and `record_hash` among the standard silver columns without saying which entities carry them. The [data-modelling standard](../standards/data-modelling.md) says "on every record". Proposal, for Rafal's approval at gate 2: reword the rule to "on every market-data record; `ops_` entities carry `run_id`, `business_date` and `known_at`, where `known_at` is when the engine wrote the record", because `source` and `record_hash` describe market data and `ops_` entities have no bronze. If Rafal reads ADR-004 as requiring all five on every silver entity, or does not accept the `known_at` meaning, this becomes an ADR amendment in this story instead, and the spec is revised.

**Layer exception.** Step 3 reads `ops/run_log/`, which is neither bronze nor reference data; [layer-boundaries](../standards/layer-boundaries.md) allows only those. The engine writes these objects itself and they are not market data. Proposal, for Rafal's approval at gate 2: "staging and silver read only bronze, reference data and the engine's run log (`ops/run_log/`, `ops_` entities)". If not approved, the run log is read from the engine's own state, and the spec is revised.

The gate result column from ADR-007 is added, additively, by the completeness gate story. `config/entities/ops_run_log.yaml` is the entity's documentation home: purpose, grain ("one row per pipeline run"), key `run_id`, not SCD2, each field's meaning and type. `run_log.py` builds the table's DDL from that file, so code and docs cannot drift. Its shape is kept to what this entity needs; the entity-config JSON Schema arrives with the dbt macros story.

**Out of the engine's hands:** one writer per environment is assumed ([ADR-003](../adr/0003-storage-and-physical-format.md)); no lock in this story.

## Tests

The engine tests run on `LocalStorage` in `tmp_path`, with fake steps; no network ([testing standard](../standards/testing.md)). Criterion 2 also runs the storage contract tests on `S3Storage` against `moto`, in-process; still no network.

| Acceptance criterion | Check |
| --- | --- |
| 1. Unique run id, one `ops_run_log` row with start, end, status, image tag, row counts | `test_run_writes_one_log_row`: two runs with steps returning 3 and 5 rows; ids differ; the published file's `ops_run_log` has both rows with the expected fields and `{"a": 3, "b": 5}`; `SW_IMAGE_TAG` set in the test shows up. The second run's published copy holds the first run's row unchanged (insert-only). `test_ops_run_log_contract`: `run_id` is unique; `run_id`, `started_at`, `status`, `image_tag`, `business_date` and `known_at` are never null; `status` takes only `succeeded`, `failed`, `interrupted` |
| 2. One storage interface, two backends chosen by config, no environment checks | `test_storage.py` runs one contract test set against `LocalStorage` and `S3Storage` on `moto`; `test_from_config` picks by `SW_STORAGE_BACKEND` and fails with exit 2 on a missing variable |
| 3. Publish last via pointer, copy, new dated name, 14 kept | `test_publish_switches_pointer`: the pointer names the new key, the previous file is byte-identical; `test_retention_keeps_14`: 16 runs leave 14 files, the current one among them |
| 4. Failing step: non-zero exit, `failed`, pointer unchanged | `test_failing_step`: exit 1, pointer and current file unchanged, `ended.json` says `failed` with the step; the next run's `ops_run_log` shows it |
| 5. Local backend covers 1 to 4, including an interrupted run | The tests above, plus `test_interrupted_run`: a step raises a `BaseException` subclass the runner does not catch (a kill); pointer unchanged, no `ended.json`, the next run lists it `interrupted` with `known_at` equal to `started_at`. `test_interrupted_publish`: storage fails on the pointer write; old version still current. `test_ended_write_fails_after_publish`: storage fails on `ended.json` after the pointer moved; exit 0, the pointer names the new file, the next run's `ops_run_log` shows the run `succeeded`, not `interrupted` |
| 6. README and engine docs updated | Review against the list below; `check_docs.py` passes |
| 7. Runbook for Rafal's first Windows run | `test_run_summary_line`: exit 0 and the last stdout line is `run <run_id> succeeded`, which the runbook names. The runbook's steps are reviewed against this spec and `check_docs.py` passes. The first DEV run on Rafal's machine is manual and not in CI |

All checks in the [README](../../README.md#run-locally) pass; fixtures are synthetic.
