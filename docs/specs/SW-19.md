# SW-19: Add the dbt project and the reference entities

Two pages at most. File `docs/specs/SW-19.md`. Frozen after the change merges; lasting facts move into docs or config first.

- **Story:** https://rrogoz-sw.atlassian.net/browse/SW-19

## Goal

Start configuration over code: entity configs drive SQL that dbt macros generate, with contracts and tests from the same config ([ADR-006](../adr/0006-transformation-and-data-testing.md), [ADR-007](../adr/0007-pipeline-engine-and-operations.md)). The first entities are `dim_instrument`, `map_instrument_source` and `ref_trading_calendar`, because prices look instruments and sessions up in them. M1 seed item 6 (reference part) in the [overview](../overview.md); deliverable 7.

## Scope

- **dbt project** in `dbt/`: `dbt_project.yml`, `profiles.yml` (lint target only), macros, generic tests, three staging models, three generated silver models.
- **Engine:** new `src/engine/reference.py` (step `reference`), `src/engine/dbt_step.py` (step `dbt`), `src/engine/dbt_models.py` (generator); `pipeline.py`: `STEPS` and `RunContext.database_path`.
- **Config:** new `config/schemas/entity.schema.json`; new `config/entities/dim_instrument.yaml`, `map_instrument_source.yaml`, `ref_trading_calendar.yaml`; `ops_run_log.yaml` gains `built_by: engine`.
- **Tooling:** runtime dependencies `dbt-core`, `dbt-duckdb`; dev dependency `sqlfluff-templater-dbt`; SQLFluff switched to the dbt templater in `pyproject.toml`, as its comment plans; `uv.lock` (generated).
- **Tests:** new `tests/unit/test_entity_configs.py`, `tests/integration/test_reference_entities.py`, fixtures `tests/fixtures/reference/` (synthetic register and calendar files, two states).
- **Docs:** see Docs to update.

Size: about 900 changed lines without generated files, fixtures and `uv.lock`, over the 400-line guide ([change conventions](../standards/change-conventions.md)). The parts depend on each other (no entity without the macro, no macro without the project). If Rafal prefers a split at gate 2: this story keeps the project, schema, generator, macros and `dim_instrument` plus `map_instrument_source`; `ref_trading_calendar` becomes its own story.

## Design

**Data flow,** per run, inside the SW-16 run on the working copy:

```text
reference/*.yaml --step reference--> <run folder>/reference/*.jsonl --source('reference', ...)-->
  staging (ephemeral, hand-written) --> silver.<entity> (generated, incremental) --> dbt tests
```

**Steps.** `STEPS = [ReferenceStep(), DbtStep()]`; `dbt` stays last, so the fetch steps of later stories go before it (story criterion 1). `RunContext` gains `database_path`, the working copy; steps put scratch files in its folder, which the run deletes.

- `reference`: reads `reference/instrument_register.yaml` and `reference/calendars/*.yaml` (paths from the repo root, like `run_log.ENTITY_FILE`; a test passes the fixture folder) and writes four newline-delimited JSON files with every key present, nulls included: `instrument_versions`, `instrument_source_ids`, `calendar_years` (calendar, year, recorded date) and `calendar_closures`. Flattening only; no logic. Returns the rows written. The files are validated by their schemas in pytest (SW-14, SW-17), so `jsonschema` stays a dev dependency.
- `dbt`: runs `dbt build` in process (`dbtRunner`) with a `profiles.yml` it writes into the run folder (dbt-duckdb, path = working copy, one thread), `--target-path` and `--log-path` in the run folder (the image's `/app` is read-only for user `sw`), `--vars` `run_id` and `reference_dir`. A failed model or test raises, so the run fails and nothing is published (SW-16). Returns the rows inserted into silver. dbt-duckdb opens the same file in the same process as the engine's connection; DuckDB shares one instance per file in a process. If the integration test shows a lock or configuration conflict, the implementer stops and raises it on the pull request instead of working around it.
- `full_refresh` is a `DbtStep` parameter for the tests; a command-line rebuild is out of scope.

**Sources and staging.** Reference files are not sources: they have no source config and no bronze. So `dbt/models/staging/reference/` holds three hand-written ephemeral models over `source('reference', ...)` (dbt-duckdb `external_location` on `var('reference_dir')`), which [layer-boundaries](../standards/layer-boundaries.md) allows. They cast types and set `known_at` = midnight UTC of the file's `recorded_date`. `stg_reference__trading_calendar` expands each calendar year into its weekdays and joins the closures (`is_session` false, `closure_name` set). Staging generated from source configs arrives with the NBP source.

**Entity config,** validated by `entity.schema.json` (Draft 2020-12, `additionalProperties: false`, a `description` on every field, so the schema documents itself):

| Key | Meaning |
| --- | --- |
| `version`, `entity`, `layer`, `description`, `grain` | as in `ops_run_log.yaml`; `entity` matches the file name and `^(dim|fact|ref|map|ops)_[a-z0-9_]+$` ([naming](../standards/naming.md)) |
| `built_by` | `dbt` (generated model) or `engine` (`ops_run_log`, DDL in `run_log.py`) |
| `input` | the staging model a `dbt` entity reads |
| `business_key`, `scd2` | key fields; an SCD2 entity is keyed by business key plus `valid_from_date` ([ADR-004](../adr/0004-physical-data-model.md)) |
| `fields[]` | `name`, `type` (`varchar`, `date`, `timestamptz`, `boolean`, `json`), `required`, `description`, optional `allowed`, optional `references` (`<entity>.<field>`) |

| Entity | Grain and key | Value fields |
| --- | --- | --- |
| `dim_instrument` | one version of an instrument's attributes; `instrument_code`, SCD2 | `current_symbol`, `asset_class` (allowed `fx`), `exchange`, `quote_ccy` |
| `map_instrument_source` | one version of a source's identifier for an instrument; `instrument_code`, `source`, SCD2 | `source_instrument_id`; `instrument_code` references `dim_instrument.instrument_code` |
| `ref_trading_calendar` | one weekday of a calendar; `calendar` (allowed `XWAR`, `NBP`), `business_date`; not SCD2 | `is_session`, `closure_name` |

Every entity also has `known_at`, `run_id`, `record_hash`, listed in its config like any field.

**Generator** `python -m engine.dbt_models [--check]` (byte-stable output, like `engine.calendars`) writes per `dbt` entity `dbt/models/silver/<entity>.sql` (one line, `{{ silver_entity() }}`) and `<entity>.yml`: description, `materialized: incremental`, `on_schema_change: fail`, `contract: enforced` with each column's `data_type` and description, `meta` with the key and value fields, and the tests: `not_null` per required field, `accepted_values` per `allowed`, `relationships` per `references`, and `unique_key` on the key plus `known_at`. Contracts and tests cannot drift from the config (story criterion 4).

**Macros** (`dbt/macros/`): `silver_entity()` reads the model's `meta`; `record_hash()` hashes the value fields in config order (cast to text, null as `\N`, joined by `chr(31)`, `md5`; [ADR-004](../adr/0004-physical-data-model.md) data rules); `generate_schema_name` so models land in `silver`, not `main_silver`; generic test `unique_key`. Load rule, insert-only: an input row is inserted only if its `record_hash` differs from the previous version of its key ordered by `known_at`; in incremental mode the previous version is the latest one in the table and input rows not newer than it are skipped; nothing is updated ([ADR-006](../adr/0006-transformation-and-data-testing.md)). `run_id` is `var('run_id')`.

**Standard columns, for gate 2.** [Data-modelling](../standards/data-modelling.md) names the columns of market-data and `ops_` records, not reference entities. Proposal: add "Reference entities (`dim_`, `map_`, `ref_`) carry `run_id`, `known_at` (midnight UTC of the reference file's `recorded_date`) and `record_hash`; their business date is `valid_from_date` if SCD2, else `business_date`." `source` is left out: in `map_` it is a business column. Like SW-16, `known_at` deviates from "comes from bronze" ([ADR-004](../adr/0004-physical-data-model.md)) because reference data has no bronze; `recorded_date` is deterministic, so full, incremental and replay agree. If Rafal reads [ADR-003](../adr/0003-storage-and-physical-format.md) as needing a literal `business_date` column, the SCD2 entities get one equal to `valid_from_date`, and the spec is revised.

**Calendar history, for gate 2.** A calendar file holds only its latest content (SW-17). Incremental runs keep earlier versions of a changed date; a full build has only the current file, with its newest `recorded_date` on every row of that year. So full equals incremental on the same input, as [ADR-006](../adr/0006-transformation-and-data-testing.md) tests, but a full rebuild loses calendar history. Proposal: accept for M1 (git holds the history; past years rarely change). The other option, a recorded date per closure in the calendar format, would be a new story.

## Tests

dbt runs on DuckDB in `tmp_path` with synthetic fixtures; no network ([testing standard](../standards/testing.md)).

| Acceptance criterion | Check |
| --- | --- |
| 1. dbt project in `dbt/`, run by the pipeline command after fetch | `test_pipeline_builds_reference_entities`: `run_pipeline` on `LocalStorage` with the fixture reference folder; exit 0; the published file holds the three tables; `ops_run_log` counts for `reference` and `dbt`. `test_dbt_is_last_step` |
| 2. Entity configs validated by a JSON Schema | `test_entity_configs_are_valid`: every `config/entities/*.yaml`, `ops_run_log.yaml` included, plus rules a schema cannot express: key and `references` name existing fields and entities, SCD2 entities have `valid_from_date`, duplicate YAML keys rejected. `test_bad_entity_config_fails`, inline cases: unknown key, missing description, bad prefix, name not matching file, unknown type |
| 3. Macros generate the three entities, SCD2, insert-only, `record_hash` | `test_reference_entities_from_state_1`: expected rows and hashes for each entity; weekdays of the fixture year with closures as non-sessions. `test_insert_only`: state 2 adds an attribute version, an identifier version and a calendar year; rows from state 1 stay byte-identical, only new rows appear; a rerun on state 2 inserts nothing |
| 4. Contracts and tests from the config; keys unique, mappings point to an instrument | `test_generated_models_up_to_date`: `dbt_models --check` exits 0. `test_duplicate_key_fails_run`: a fixture register with two versions on one `valid_from_date` fails `unique_key`, the run fails, the pointer is unchanged. `test_relationship_test_fails`: a `dim_instrument` row deleted in a built database makes `dbt test` fail on `relationships` |
| 5. Full and incremental builds give identical tables | `test_full_equals_incremental`: incremental on state 1 then state 2, against a full build on state 2; all columns except `run_id` identical, sorted by key and `known_at` |
| 6. Entity docs updated | Review against the list below; `check_docs.py` passes |

All checks in the [README](../../README.md#run-locally) pass, including `sqlfluff lint dbt` on the dbt templater.
