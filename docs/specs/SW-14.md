# SW-14: Add the instrument register for the M1 currency pairs

Two pages at most. File `docs/specs/SW-14.md`. Frozen after the change merges; lasting facts move into docs or config first.

- **Story:** https://rrogoz-sw.atlassian.net/browse/SW-14

## Goal

Create the [instrument register](../glossary.md) for `FX.EURPLN`, `FX.USDPLN` and `FX.CHFPLN` with their NBP identifiers, and a JSON Schema that keeps it valid. The NBP connector and the later `dim_instrument` and `map_instrument_source` then have one reviewed source of identity ([ADR-004](../adr/0004-physical-data-model.md), D6). M1 seed item 2 in the [overview](../overview.md).

## Scope

- **Reference data:** new `reference/instrument_register.yaml`.
- **Config schema:** new `config/schemas/instrument_register.schema.json`.
- **Test:** new `tests/unit/test_instrument_register.py`.
- **Tooling:** dev dependencies `pyyaml`, `jsonschema`, `types-PyYAML`, `types-jsonschema` in `pyproject.toml`, and `uv.lock` (generated).
- **Docs:** [glossary](../glossary.md).

## Design

**File format.** YAML with comments, validated by a JSON Schema ([ADR-009](../adr/0009-repository-and-standards.md)). Names follow the [naming standard](../standards/naming.md). The first line comment says what the file is for and that changes need Rafal (code owners, [change conventions](../standards/change-conventions.md)).

**Shape.** A mapping keyed by permanent code, so a code can appear only once. Every fact that can change is a list of versions with `valid_from_date` and `recorded_date`, so the register is point in time ([ADR-004](../adr/0004-physical-data-model.md), data rules) and feeds SCD2 entities later.

```yaml
# Instrument register: identity and source identifiers (ADR-004). Changes need Rafal's approval.
version: 1
instruments:
  FX.EURPLN:
    versions:                       # attributes, insert-only; newest last
      - valid_from_date: "2002-01-02"
        recorded_date: "<date of this change>"
        current_symbol: EURPLN
        asset_class: fx
        quote_ccy: PLN
    source_ids:                     # identifier map, one entry per source and version
      - source: nbp
        source_instrument_id: A/EUR
        valid_from_date: "2002-01-02"
        recorded_date: "<date of this change>"
```

| Field | Meaning | Rule in the schema |
| --- | --- | --- |
| key under `instruments` | permanent code | `propertyNames` pattern `^FX\.[A-Z]{3}[A-Z]{3}$`; other asset-class patterns are added with their first instrument |
| `current_symbol` | symbol shown today; FX: base and quote without separator | required string |
| `asset_class` | asset class | required, enum `fx` (additive later) |
| `exchange` | MIC of the listing exchange | optional; FX pairs have none |
| `quote_ccy` | currency of the price (ISO 4217); "currency" in ADR-004 | required, `^[A-Z]{3}$` |
| `source` | source name, as in its future source config | required, enum `nbp` |
| `source_instrument_id` | the source's own identifier; NBP: table and code, as in `/api/exchangerates/rates/A/EUR/` | required string |
| `valid_from_date`, `recorded_date` | when the fact holds; when we wrote it | required, quoted ISO dates (`format: date`); quoted so YAML keeps them as strings |

- `valid_from_date` is `2002-01-02`, the first NBP table A of 2002, the start of the history in [ADR-005](../adr/0005-sources-and-ingestion.md). `recorded_date` is the date the implementation commits the register.
- `additionalProperties: false` everywhere, so a typo fails. Each field has a `description` in the schema, which is the field's documentation home.

**Rules a JSON Schema cannot express,** checked in the test:

- **Unique codes:** YAML parsers keep the last of two equal keys silently. The test loads YAML with a `SafeLoader` subclass that rejects duplicate keys, so a repeated code fails before the schema runs; the schema then enforces the code pattern.
- An FX code's quote currency equals `quote_ccy`, and `current_symbol` equals the code without `FX.`.
- One source identifier maps to one instrument (no two instruments share `source` plus `source_instrument_id`), so the connector never has to guess ([ADR-004](../adr/0004-physical-data-model.md), integrity).
- `versions` and `source_ids` are in ascending `valid_from_date` order, so "newest last" holds.

The loader and checks live in the test module for now; no engine code reads the register yet.

## Tests

| Acceptance criterion | Check |
| --- | --- |
| 1. Register lists the three instruments with the ADR-004 fields | `test_register_lists_m1_instruments`: codes are exactly `FX.EURPLN`, `FX.USDPLN`, `FX.CHFPLN`; each has a version with all required fields and an `nbp` identifier `A/EUR`, `A/USD`, `A/CHF` |
| 2. JSON Schema validates the register, unique codes, `FX.<base><quote>` | `test_real_register_is_valid` validates the real file with `jsonschema` (Draft 2020-12, format checks on) |
| 3. Passes on the real register, fails on a synthetic bad one | `test_bad_register_fails`, parametrized over inline synthetic YAML: duplicate code, code `FX.EUR-PLN`, missing `quote_ccy`, unknown field, bad date, FX quote currency not matching `quote_ccy`, one NBP identifier on two instruments, versions out of order. Each must raise |
| 4. Docs updated | Review: glossary entries below; `check_docs.py` passes |

All checks in the [README](../../README.md#run-locally) pass, including `check_no_real_data.py` (the register holds identifiers, not market data; `.json` is allowed in `config/`). Testing rules: [testing standard](../standards/testing.md).
